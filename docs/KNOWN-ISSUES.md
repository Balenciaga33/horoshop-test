# Відомі проблеми та drift

Проблеми / невідповідності, помічені під час побудови сьюту проти `https://shop703343.horoshop.ua`.

Правило сьюту: **асертимо фактичну поведінку**, тримаємо тести зеленими й явно фіксуємо drift тут. У коді можна додати Playwright-анотацію через `annotateKnownIssue('ID', '…')` — ID має збігатися з цим файлом.

ID стабільні (`U*`, `A*`, `C*`) і не залежать від порядку в документі.

---

## UI / браузер

### U1 — Кошик у headless Chromium отримує `BAD_CSRF`

|                    |                                                                |
| ------------------ | -------------------------------------------------------------- |
| Очікування         | UI-тести стабільно працюють у headless                         |
| Факт               | `/_widget/ajax_cart/init/` часто падає з `BAD_CSRF` у headless |
| Ризик              | False fail у CI без headed / спеціального обходу               |
| Що робимо в тестах | UI project: `headless: false` у `playwright.config.ts`         |
| Evidence           | `playwright.config.ts`, `helper/cart.helper.ts`                |

### U2 — Порожній checkout не показує inline-помилок

|                    |                                                                |
| ------------------ | -------------------------------------------------------------- |
| Очікування         | Порожні обов’язкові поля → видимі повідомлення про помилку     |
| Факт               | Поля не HTML5-`required`; основний гейт — `disabled` на submit |
| Ризик              | «Немає тексту помилки» ≠ відсутність валідації                 |
| Що робимо в тестах | Перевіряємо disabled submit + порожні значення                 |
| Evidence           | `tests/ui/checkout.validation.spec.ts`; annotation `U2`        |

### U3 — Порожнє ПІБ не блокує submit

|                    |                                                                   |
| ------------------ | ----------------------------------------------------------------- |
| Очікування         | Ім’я отримувача обов’язкове для активації оформлення              |
| Факт               | Після валідного заповнення очищення ПІБ лишає submit **активним** |
| Ризик              | Можливе оформлення без імені (залежить від серверної перевірки)   |
| Що робимо в тестах | Документуємо поточну поведінку (`expectSubmitEnabled`)            |
| Evidence           | `tests/ui/checkout.validation.spec.ts`; annotation `U3`           |

### U4 — Видалення товару з popup-кошика майже неклікабельне

|                    |                                                                    |
| ------------------ | ------------------------------------------------------------------ |
| Очікування         | Кнопка remove у popup стабільно клікається                         |
| Факт               | Елемент часто з `opacity/height ≈ 0`; надійніше remove на checkout |
| Ризик              | Крихкі UI-тести на popup remove                                    |
| Що робимо в тестах | Видалення через checkout (`a.j-remove-p` + confirm dialog)         |
| Evidence           | `tests/ui/cart.update.spec.ts`                                     |

## API

### A1 — Бізнес-помилки повертаються з HTTP 200

|                          |                                                                     |
| ------------------------ | ------------------------------------------------------------------- |
| Очікування (типове REST) | Невалідний login → `401`/`403`                                      |
| Факт                     | Майже завжди HTTP `200`, результат у полі `status` (`OK`/`ERROR`/…) |
| Ризик                    | Клієнти, що дивляться лише на HTTP-код, «проковтнуть» помилку       |
| Що робимо в тестах       | Асертимо `status` + Zod-схему body                                  |
| Evidence                 | `tests/api/auth.spec.ts`, catalog specs                             |

### A2 — Різні статуси для «немає токена» і «битий токен»

|                    |                                                                       |
| ------------------ | --------------------------------------------------------------------- |
| Факт               | Без токена → `AUTHORIZATION_ERROR`; невалідний токен → `UNAUTHORIZED` |
| Ризик              | Один негативний тест «на authz» недостатній                           |
| Що робимо в тестах | Окремі кейси + окремі Zod-схеми                                       |
| Evidence           | `tests/api/catalog.export.spec.ts`; annotation `A2`                   |

### A3 — `orders/export` на цьому магазині недоступний

|                    |                                                                                                |
| ------------------ | ---------------------------------------------------------------------------------------------- |
| Очікування         | `POST /api/orders/export/` як у частини інтеграцій / Notion                                    |
| Факт               | `status: UNDEFINED_FUNCTION`; робочий read — `orders/get`, але зараз `EMPTY` (немає замовлень) |
| Ризик              | Тести orders без seed даних слабкі або неможливі                                               |
| Що робимо в тестах | Orders у сьюту поки не покриваємо як основний happy path                                       |
| Evidence           | Ручний probe під час дослідження API                                                           |

### A4 — Немає live OpenAPI (`/api/doc.json`)

|                    |                                                                 |
| ------------------ | --------------------------------------------------------------- |
| Очікування         | Машинально-читаний контракт з API                               |
| Факт               | Документація в Notion; у репо — `openapi/horoshop.openapi.json` |
| Ризик              | Контракт може роз’їхатися з релізами Horoshop                   |
| Що робимо в тестах | Локальний OpenAPI + Zod; оновлювати обидва при drift            |
| Evidence           | `openapi/horoshop.openapi.json`, `helper/openapi.helper.ts`     |

## Каталог / контент магазину

### C1 — Батьківська категорія «Косметика» може давати 404

|                    |                                                                                                |
| ------------------ | ---------------------------------------------------------------------------------------------- |
| Факт               | URL на кшталт `/kosmetika/` нестабільний/404; навігація йде по реальних slug товарів/категорій |
| Ризик              | Тести «відкрити косметику з меню» падають без вини коду сьюту                                  |
| Що робимо в тестах | Використовуємо перевірені slug з `data/*.json`                                                 |
| Evidence           | `data/products.data.json`, `data/catalog.data.json`                                            |

## Як оновлювати цей файл

1. Знайшли drift → новий ID (`U5`, `A5`, …)
2. Опишіть очікування / факт / ризик / що робить сьюти
3. Додайте `annotateKnownIssue` у відповідному тесті
4. Не «ховайте» drift зеленим асертом без запису тут
